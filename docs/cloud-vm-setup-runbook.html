01

Access model

This app is reached only over Tailscale — never over the VM's public IP. The public IP exists solely so you can SSH in to administer the box. Keep this in mind through every step below: locking the cloud firewall down to just SSH (next section) does not break the app, because Tailscale never needs an inbound firewall rule to work — it connects outbound and either finds a direct path or relays through Tailscale's own servers.

02

Lock down the cloud firewall (NSG)

An NSG (Network Security Group, Azure's term — other clouds call this a security group) is a firewall that sits in front of the VM at the cloud provider's network layer, before traffic ever reaches the VM's own operating system. Separate from anything configured inside Linux.

  1. In the cloud console, find the VM's network security rules.
  2. Confirm exactly one inbound allow rule exists: TCP port 22 (ideally scoped to a known admin IP range, not "Any").
  3. Remove every other inbound allow rule you find — quickstart-created VMs sometimes have 80/443/3389 pre-opened.

Everything else stays closed by the provider's default deny — you don't need to add explicit deny rules.

Verify from outside, once the app is running (Section 11) — from a network that is not on the tailnet, confirm only port 22 responds:
powershell — run from any Windows machine off the tailnet
$ip="<public-ip>"; 22,80,443,1883,5432,6379,9000,9001,3000 | ForEach-Object { $r = Test-NetConnection -ComputerName $ip -Port $_ -WarningAction SilentlyContinue; "$_ -> $(if ($r.TcpTestSucceeded) {'OPEN'} else {'closed/filtered'})" }

Only 22 should print OPEN.

03

Connect over SSH, confirm sudo

connect
ssh -i "<path-to-private-key>" <ssh-username>@<public-ip>
The single biggest source of confusion this rollout

If you're on Windows, every command from here on runs in two different worlds: your local PowerShell (before the SSH connection) and the VM's own Linux shell (after it connects). Watch the prompt — PS C:\...> means you're still local; user@host:~$ means you're on the VM. Every "this Linux command is failing" error hit during this rollout — ssh-keygen -N "" failing with "option requires an argument," and a <<'EOF' heredoc failing with "missing file specification" — turned out to be the same command typed into the wrong prompt. If a plain Linux command throws a Windows-flavored error, that's the tell.

SSH sessions also time out from inactivity — if a command that worked five minutes ago suddenly fails the same way, reconnect and check the prompt again before assuming anything else is wrong.

confirm passwordless sudo, once connected
sudo -n true && echo "sudo OK" || echo "a real password is required"

If a real password is required and none was given to you, use the cloud console's password-reset feature for the VM (Azure: the "Reset password" blade) — it sets a Linux account password without disturbing your existing SSH key.

04

Install Docker Engine

Docker Engine, not Docker Desktop — Desktop is for workstations with a GUI and has licensing terms that don't apply here.

on the VM
sudo apt update && sudo apt upgrade -y
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER

Log out and back in (or run newgrp docker) so the group membership takes effect before continuing.

05

Repo access

  1. Generate a deploy key on the VM itself

    So the private half never has to leave the machine that uses it. No passphrase flag needed — just press Enter twice at the prompts, which also sidesteps the Windows/Linux quoting issue from Section 3 entirely.

    on the VM
    ssh-keygen -t ed25519 -C "roshai-pilot-vm" -f ~/.ssh/deploy_key
cat ~/.ssh/deploy_key.pub
  2. Add the public key as a read-only deploy key
    On the client's repo from Section 00 — leave "allow write access" unchecked.
  3. Point SSH at this key for GitHub specifically
    on the VM
    cat >> ~/.ssh/config <<'EOF'
Host github.com
  IdentityFile ~/.ssh/deploy_key
  IdentitiesOnly yes
EOF
  4. Clone the repo, on the confirmed branch
    on the VM
    git clone --branch development git@github.com:<org>/<repo>.git
cd <repo-folder>
If pushing from your own dev machine too

Swapping between an org repo and a client repo on the same Windows machine via saved HTTPS credentials is a common source of a confusing "repository not found" (which is actually a stale cached credential, not a real permissions problem). Remove the git:https://github.com entry in Windows Credential Manager before switching which repo you're pushing to.

06

Tailscale identity: auth key & hostname

  1. Generate a reusable auth key
    Tailscale admin console → Settings → Keys → Generate auth key. Tick Reusable, tag it tag:server.
  2. Get the tailnet's MagicDNS domain
    Settings → DNS — looks like taildXXXXX.ts.net.
  3. Pick a hostname no other device on this tailnet is already using
    This is the step most likely to bite. Check the admin console's device list first.
Hit this rollout — hostname collision

Reusing an existing device's hostname (e.g. an existing laptop deployment's) doesn't produce an error — Tailscale silently registers the new device under an auto-suffixed name instead (roshai-control-tower → roshai-control-tower-1). That auto-suffixed name then has to exactly match two other places that reference it literally in this stack's config, or things fail in confusing, disconnected-looking ways:

  • The TLS cert request in tailscale-cert-refresh — fails with invalid domain "X"; must be one of ["X-1"] if the configured hostname doesn't match what was actually assigned.
  • MTX_WEBRTCADDITIONALHOSTS (MediaMTX's advertised WebRTC address) — if wrong, video signaling succeeds but no media ever plays, with zero error message pointing at the real cause.

If it happens: just set TS_HOSTNAME in docker/.env (next section) to the actual assigned name, or pick a genuinely distinct one and let it re-register — either way, confirm the admin console shows the name you expect before moving on.

07

Create docker/.env

on the VM
cp docker/.env.example docker/.env
nano docker/.env

Generating secrets

on the VM — run once per secret needed
openssl rand -hex 24
Use -hex, not -base64

Base64 output can contain /, +, = — any of which silently corrupts a postgresql://user:pass@host/db-style connection string if the password lands there unescaped. This rollout lost real time chasing a Postgres "invalid credentials" error that was actually just an un-encoded slash in a generated password. Hex output (0-9a-f only) never has this problem.

Two real mistakes made this rollout, both silent

Duplicate lines. An edit to DATABASE_URL left two DATABASE_URL= lines in the file — one stale, one correct. Whichever the parser reads last silently wins, so every "fix" to the wrong copy kept failing with no obvious reason. After any edit: grep -c "^VARNAME=" docker/.env should print exactly 1.

The placeholder that looks real. VIDEO_RTSP_BASE_URL's template value is rtsp://roshai-control-tower.{tailnet-domain}:8554 — the {tailnet-domain} is literal, unsubstituted text, easy to mistake for a filled-in example. It has to be manually replaced. Don't add a trailing path — the backend appends /AUTO itself.

Save (Ctrl+O, Enter, Ctrl+X in nano), then lock the file down:

on the VM
chmod 600 docker/.env
08

Tailscale container networking

This section exists because of a two-round bug this rollout spent real time on — if the compose file already has this fix, skip to Section 09. If setting this project up fresh on a new VM and video/WebRTC doesn't work, come back here.

What the fix looks like, in docker-compose.yml

The tailscale service needs all three of these together — two alone were not enough:

docker-compose.yml — tailscale service
  tailscale:
    cap_add:
      - NET_ADMIN
      - NET_RAW
    devices:
      - /dev/net/tun:/dev/net/tun
    environment:
      TS_USERSPACE: 'false'
      # ...existing TS_AUTHKEY / TS_HOSTNAME / etc.

Why this matters

Without real kernel network access, Tailscale's own startup script falls back to --tun=userspace-networking — visible directly in its boot log. That mode carries TCP-based traffic fine (which is why HTTP/WHEP signaling and RTSP's TCP control channel work), but can't properly carry WebRTC's actual UDP media path. Symptom: video signaling succeeds (201 responses) but no video ever plays, cycling create→silence→delete→retry indefinitely.

Diagnostic checklist, in order

  1. Check the actual mode
    on the VM
    docker compose -f docker/docker-compose.yml logs tailscale | grep -i userspace
    Empty means real networking is active. Any output means it's still falling back.
  2. Confirm the device exists, both places
    on the VM
    ls -la /dev/net/tun
docker compose -f docker/docker-compose.yml exec tailscale ls -la /dev/net/tun
    If missing on the host: sudo modprobe tun, then recheck.
  3. Confirm the capability actually applied to the running container
    on the VM
    docker inspect $(docker compose -f docker/docker-compose.yml ps -q tailscale) --format "CapAdd: {{.HostConfig.CapAdd}}"
    Should show NET_ADMIN. A stale un-recreated container won't.
  4. Rule out AppArmor
    on the VM
    sudo dmesg | grep -i apparmor | tail -30
    Look for a DENIED line naming a network/tun-related operation near the container's start time. On this rollout's VM, all four checks above came back clean and TS_USERSPACE: 'false' was still the missing piece — try that first if you're short on time.
Recreating tailscale alone will take the whole app down

traefik, tailscale-cert-refresh, and mediamtx all use network_mode: service:tailscale — they share that specific container's network namespace instead of having their own. Recreating tailscale by itself leaves those three attached to the now-removed old namespace, and the login page starts returning "refused to connect." Always recreate all four together:

on the VM
docker compose -f docker/docker-compose.yml up -d --force-recreate tailscale tailscale-cert-refresh traefik mediamtx
09

Build and start

on the VM
docker compose -f docker/docker-compose.yml up -d --build

Give it a minute, then confirm every service is genuinely healthy, not just running:

on the VM
docker compose -f docker/docker-compose.yml ps

Every row should show (healthy), not just Up — those aren't the same thing.

Local dev, for reference: a gitignored docker-compose.override.yml restores dev-only host ports on a laptop. Since this project always invokes Compose with an explicit -f, Compose's automatic override discovery doesn't apply — local dev needs it passed explicitly: docker compose -f docker/docker-compose.yml -f docker/docker-compose.override.yml up. The VM never has this file at all.
10

Run the database migration, seed the first admin

The running backend container intentionally doesn't have the Prisma CLI (stripped from the production image to keep it small) — build a one-off image from the earlier build stage instead:

on the VM
docker build --target build -f docker/backend.Dockerfile -t roshai-migrate .
The network name isn't your folder name

It comes from the name: field at the top of docker-compose.yml (e.g. roshai-control-tower), regardless of what the repo folder you cloned into is actually called. Confirm with docker network ls if the next commands say "network not found."

on the VM — migrate
docker run --rm --network roshai-control-tower_default --env-file docker/.env roshai-migrate sh -c "cd backend && npx prisma migrate deploy"
on the VM — seed the first admin
docker run --rm --network roshai-control-tower_default --env-file docker/.env roshai-migrate sh -c "cd backend && npx prisma db seed"
Watch for a truncated command

A pasted multi-line command that gets cut off mid-string (an open quote never closed) leaves the shell silently waiting for more input — it looks like nothing happened. Ctrl+C to cancel, then re-paste the complete command on one line.

If backend was unhealthy before this, it should recover within a healthcheck cycle or two once the tables exist. Force it if not: docker compose -f docker/docker-compose.yml restart backend.

11

Verify

  • Tailscale admin console shows the VM as a connected device, under the name you expected.
  • From a device on the tailnet, the app loads at https://<TS_HOSTNAME>.<TS_TAILNET_DOMAIN>.
  • Log in with the seeded admin email/password.
  • Trigger a test e-stop and confirm it's recorded in the audit log.
  • From a device off the tailnet, the NSG check from Section 02 still shows only port 22 open.
12

Hand off to the bot team

Once the VM is confirmed working, they need exactly two values and one pipeline setting:

WhatValue
MQTT brokerwss://<TS_HOSTNAME>.<TS_TAILNET_DOMAIN>/mqtt
RTSP ingest baseThe VIDEO_RTSP_BASE_URL value from docker/.env
GStreamer pipeline flagprotocols=tcp on rtspclientsink — UDP RTP media was found to drop after ~10s over the tailnet
Nothing switches over automatically

If this VM is replacing an earlier deployment (a laptop, a different VM), the bot keeps talking to whatever it's currently configured for until someone on the bot team explicitly repoints it. The two deployments run as fully independent systems with separate databases in the meantime — confirm the cutover with them directly rather than assuming it happened.
