01

Component profile

Every service in the current stack, sized and license-checked against how it's actually used here — not against generic best-case footprints. Two components (marked below) carry a licensing detail worth acting on before this scales into a client-facing production system.

Postgres

postgres:16-alpine
Clear

Light today; grows with audit-log retention.

PostgreSQL License — fully permissive, no restriction on commercial or client use.

Fine as-is. Add a retention/partitioning plan before the fleet scenario (§3).

Redis

redis:7-alpine
Clear

Trivial — holds only operator login sessions (~150 bytes, 8h TTL) and OIDC login flow state (5min TTL, single-use). Telemetry is deliberately kept out of Redis entirely, to avoid a round-trip on high-frequency bot messages — so this footprint doesn't grow with bot count, vehicle count, or concurrent sessions in phase 2.

The 7-alpine tag now resolves to Redis 7.4.11 (RSALv2 / SSPLv1, not the BSD license that tag implied pre-2024) — but that license targets reselling Redis as a hosted service to third parties, which is nowhere near what this does. Practically a non-issue as used here.

Optional housekeeping: valkey/valkey:7-alpine is a zero-cost, protocol-compatible BSD-3-Clause swap, and matches where Ubuntu/Debian/Alpine packaging is already heading — worth doing, but not fixing a real risk.

MinIO

minio/minio:latest
Flag — act on this soon

Light at pilot scale; grows with media volume.

AGPLv3 — but the license itself is not the real issue. AGPL's network-copyleft clause triggers on modifying the source and exposing that modified version to outside users directly; this backend runs it unmodified, purely as internal infrastructure, and end users never touch MinIO directly (all access is proxied through the backend). That's a well-established, low-risk way to run AGPL software — the earlier framing overstated this.

The real, concrete problem: the upstream project is dead. Verified directly against GitHub and Docker Hub (not just secondary sources): MinIO Inc. froze the official minio/minio Docker image at RELEASE.2025-09-07 — it will never receive another update — and archived the GitHub repository entirely on April 25, 2026 ("THIS REPOSITORY IS NO LONGER MAINTAINED"), redirecting users to the commercial AIStor product. A high-severity (CVSS 8.1) privilege-escalation bug, CVE-2025-62506, was patched only in a source-only release (its own notes tell users to clone and build the container themselves) — so this exact tag is permanently unpatched against it, and will be against every future finding too.

That specific CVE needs a restricted service-account/STS token to exploit, and this backend currently authenticates with MinIO's root credential — so today's setup happens not to be exposed to this one. That's incidental, not a fix: an abandoned image with zero future patches is a standing risk regardless of which CVE lands next. Recommend migrating off this image soon, independent of pilot-vs-fleet scale — either to an actively maintained community fork (e.g. pgsty/minio, ~1.8k GitHub stars, still shipping releases as of mid-2026) as a stopgap, or straight to real cloud object storage (S3/Blob/GCS) per §5, which the backend can adopt with minimal code change since it already speaks the S3 API.

eclipse-mosquitto:2
Clear

Very light — edge-class footprint.

EPL 2.0 / EDL 1.0 dual license — permissive. Already the reason this was chosen over EMQX, which moved to a restrictive BSL.

Fine as-is at both scenario sizes.

MIT — no concern. Fine as-is.

Tailscale

tailscale/tailscale
Clear

Light sidecar.

Client (tailscaled) is BSD-3-Clause; the coordination control plane is a separate commercial hosted service.

Free plan (2026): 6 users, unlimited user devices, but capped at 50 tagged/infra resources and 1,000 ephemeral-resource-minutes/month. Bots and VMs count as tagged resources, not user devices — a pilot is nowhere near the cap, but the confirmed 30-bot fleet (§3) plus its VM(s) sits close enough to that cap to plan around now, not later.

Verdict: does MinIO need to change?

Not urgent today → real risk, act on your own timeline

Yes, but it's not an emergency. Nothing is being actively exploited, and the one known CVE found doesn't even apply to this setup today — it needs a restricted service-account token to trigger, and this backend authenticates with MinIO's root credential. So there's no incident to react to right now.

What makes it a real "needs to change" rather than a "nice to have": the upstream project is abandoned — verified directly against GitHub and Docker Hub, not just a secondary source. MinIO Inc. froze the official Docker image at RELEASE.2025-09-07 and archived the GitHub repo on April 25, 2026. That means zero security patches, for anything, ever again, on this exact image. The gap between "what's patched" and "what's found" only grows from here.

Does running it inside an isolated VM actually change that? Meaningfully, yes — but it doesn't remove the risk, it changes its shape. MinIO's port is never exposed to the public internet or even to Traefik here; only the backend, inside the same Docker network, can reach it, so an outside attacker with no existing foothold can't touch it directly. That's real and worth crediting. What it doesn't cover:

  • Defense-in-depth: the isolation only holds if nothing else is ever compromised. If an attacker gets any foothold inside the network — a different vulnerability, a leaked credential, a compromised backend dependency — an unpatched MinIO stops being a second wall and becomes the easiest thing to fully compromise once they're in. It's specifically the component holding every stored report and media file.
  • Future CVEs, not just this one: today's specific bug happens not to apply because of the root-credential setup — that's incidental, and the next one might not care. An abandoned image accumulates unpatched vulnerabilities indefinitely, including in its base OS layer, not just MinIO's own code.
  • Vendor/compliance posture: independent of technical exploitability, "running an archived, unmaintained project with a known unpatched CVSS 8.1 CVE" is the kind of finding a client security review or questionnaire flags on its own.

Net: genuinely not urgent given the isolation, but cheap to fix and only gets riskier the longer it's left — worth doing on a relaxed timeline. Two paths, either works:

  • Cheaper, near-term: swap the image tag to an actively maintained community fork (e.g. pgsty/minio) — same S3 API, no application code changes.
  • Better, long-term: move to real cloud object storage (S3/Blob/GCS, §5) — a small, contained backend change since the app already speaks the S3 API, and it solves the fleet-scale retention/backup work (§3) at the same time. The stronger choice if cloud hosting is the direction anyway, since it avoids fixing a dying dependency twice.

Pilot — one bot, one vehicle

Scope: PDF reports under 5 MB and one live video stream. Every service in §1 is lightweight at this scale, so the sizing question here is really "cloud VM, on-prem VM, or a laptop" — checked below.

1 · Recommended — small cloud VM
vCPU2
RAM4–8 GB
Disk60–100 GB
Cost$25–50/mo
  • e.g. AWS t3.medium/large, Azure B2s/B2ms, or a 4–8 GB DigitalOcean/Linode droplet — one WebRTC stream needs no serious CPU unless MediaMTX is actively transcoding.
  • Pick the region physically nearest the client site, and run a real tailscale ping test from that site before committing — that's what determines whether the extra network hop matters for the safety-critical MQTT e-stop path.
  • Ubuntu 22.04/24.04 LTS, Docker Engine + Compose plugin (see §6 on why not Windows/WSL2 — no Docker Desktop, no licensing question at all).
2 · Secondary — client-hosted on-prem VM
vCPU2
RAM4–8 GB
Disk60–100 GB
CostHardware only
  • A dedicated small box at the client site (mini-PC/NUC-class or small server) — same sizing as the cloud VM, but no recurring bill and everything stays on the client's premises.
  • Safer than the laptop tier: it's a dedicated, always-on machine, not something a person needs back for their own work or that drops the stack when the lid closes.
  • Still carries the on-prem tradeoffs cloud avoids: hardware failure has no automatic redundancy, patching/updates are now someone's manual job, and if the machine freezes up and becomes unreachable — even over Tailscale — there's no remote way in; someone has to be physically on-site to power-cycle it. Backups (Postgres dump + MinIO sync) need to be shipped off-site by hand, not a built-in feature.
  • Right call when the client wants the pilot's data to stay strictly on-premises, or simply prefers owning a physical box over a recurring cloud line item.
3 · Last resort — employee's office laptop

Workable only as a stated-temporary bridge before either option above is in place — not a real deployment tier, and worth putting the caveats below in writing so it's never mistaken for one.

  • Sleep/lid-close drops the whole stack; no redundancy; the laptop's owner can't take it home or reimage it without warning.
  • Needs Docker Desktop on Windows, which is free only if the client is both under 250 employees and under $10M in annual revenue — it's an AND, not an OR, so headcount alone doesn't confirm free eligibility. Worth checking the client's revenue too, or confirming directly against Docker's published terms, before assuming this costs nothing.
  • Set a date/trigger in writing for when this graduates to option 1 or 2 above.

Does cloud still win at one-bot scale? Yes — a smaller footprint doesn't weaken the case, it sharpens it.

  • Cloud's advantages — managed hardware redundancy, automatic snapshots instead of a hand-rolled backup script, and a remote way in even if the machine itself freezes up and stops responding — are about who carries ongoing operational risk, not how many bots are being served. A dead disk or a frozen machine is exactly as disruptive with one bot as with fifteen.
  • The only thing that actually scales with bot count is cost — and at $25–50/month, there's essentially no self-hosting saving worth trading that risk for.

Tier 2 (on-prem VM) is a real, legitimate step up from the laptop tier — a dedicated always-on box is far more reliable than a shared laptop. But choosing it means deliberately taking on the hardware-failure, patching, and backup work that cloud would otherwise absorb — it's a tradeoff being made, not a free upgrade. Tier 3 (laptop) stays a last resort: fine as a stated-temporary bridge, never the pilot's real home.

03

Fleet — multi-bot, multi-vehicle

Confirmed inputs: 30 bots/vehicles by the 6–12 month mark (firming up the earlier 15+ working figure), each pair running multiple test sessions per day; video remains on-demand only, not always-on per bot. Two things follow from this: video still isn't the dominant sizing driver (MediaMTX load tracks concurrent viewers, not fleet size or session count) — but doubling the fleet size and running several sessions per pair per day meaningfully raises sustained Postgres write volume, daily audit-log row count, and object-storage growth rate, all of which move faster than the earlier 15+ estimate assumed.
Revised sizing for 30 bots × multiple sessions/day — load-test before locking in
vCPU8–16
RAM24–32 GB
DiskGrows w/ usage
TailscaleStandard plan
  • vCPU (6–12 → 8–16): raised for headroom, not because Mosquitto/Postgres are near their ceiling — a single Mosquitto instance handles thousands of connections and 30 concurrent bots is trivial for it. The extra headroom is for concurrent report/PDF generation, WebSocket fan-out to the dashboard when many bots run sessions at once, and the higher sustained (not peak) Postgres write rate from several sessions/day across 30 pairs rather than one.
  • RAM (16–24 GB → 24–32 GB): Postgres benefits most — a faster-growing audit-log table (30 pairs × multiple sessions/day means several times the daily row count the earlier estimate assumed) needs more working-set room to keep query/report performance from degrading as the table grows between archival passes.
  • Disk — now the sharpest planning risk, not a "someday" item: object storage (wav/jpg/pdf) and audit-log rows both grow directly with sessions/day × 30 pairs, not bot count alone. The concrete number needed from the client is average sessions per pair per day (right now specified only as "multiple") and average file size per session — multiply those by 30 and by the intended retention window and that's the real disk figure. Don't finalize a disk size without it.
  • Tailscale: 30 confirmed bots plus the production VM(s) already sit close to the free tier's 50-tagged-resource cap, before counting any subnet routers, staging bots, or future growth past 30. At this fleet size, budget the paid Standard plan ($8/user/mo) — or a self-hosted Headscale control plane — into the proposal now; this is no longer a "watch for later" item.

Two numbers would turn this from a load-test starting point into a final spec: telemetry message rate per bot (frequency and payload size, sets Postgres/Mosquitto load) and average sessions per pair per day (sets disk growth rate). See the open item in §7.

Storage growth model. Only PDF reports (≤5 MB, capped in code today) actually exist yet — wav audio and jpg images are a fleet-scenario addition with no implementation to measure yet, so the figures below are an illustrative planning exercise, not a spec. The shape of the model is what matters: storage grows as sessions/day × 30 pairs × avg. file size/session, and retention policy decides how many days of that you're carrying at once.

Report (PDF, capped)≤ 5 MB
Audio (WAV, illustrative)~2 MB/min
Images (JPG, illustrative)~1–3 MB each

Worked example only — get real numbers from the client before using this to size disk: a 10-minute WAV recording (~20 MB) plus 5 JPG stills (~10 MB) plus a report (~5 MB) puts one session around ~35 MB. At an illustrative 3 sessions/pair/day, that's 3 × 30 × 35 MB ≈ 3.2 GB/day, roughly ~95 GB/month and ~1.1 TB/year if nothing is ever archived. WAV duration is the single biggest lever in this model — a 30-minute session instead of 10 roughly triples the total.

Retention, not just capacity, needs a decision before this ships: keep recent sessions (e.g. last 30–90 days) in normal ("hot") storage for fast access, then either delete or move older ones to a cheaper archive tier. Real cloud object storage (S3/Blob/GCS, §5) does this automatically via lifecycle policies; self-hosted MinIO needs a scheduled job to do the same thing by hand. Also worth a check with the client on whether their industry imposes a minimum retention period for test/audit records — that's a compliance question for them, not an engineering default to assume either way.

04

Does the current stack scale to the fleet?

Component by component:

PostgresScales

A single well-indexed instance handles tens of millions of audit-log rows without issue. The path forward — partition by date, add a read replica for reporting — is incremental, not a rearchitecture.

MinIOFlag

Capacity isn't the issue — the image itself is: upstream is archived and the official Docker image gets no further security patches (§1). This is worth fixing before the fleet scale-up regardless of the licensing question, by moving to a maintained fork or real cloud object storage (§5).

MosquittoScales

A single instance is documented to handle thousands of connections — comfortably above realistic multi-bot fleet sizes.

MediaMTXScales

De-risked by the on-demand-only video model — load tracks concurrent viewers, not fleet size, so even at 30 bots this stays modest as long as simultaneous-watch count stays low. Worth a ceiling check with the client on how many operators would realistically watch at once across a 30-bot test day, but no longer the primary scaling driver.

RedisScales

Trivially — it holds only operator login/OIDC state, never telemetry, so its memory footprint tracks concurrent human dashboard users, not bot count or session volume. Not a phase-2 sizing concern.

Traefik / TailscaleScales

Traefik scales fine; Tailscale's tagged-resource cap is a plan/cost question, not a technical limit.

Bottom line: the stack scales technically. The two things worth fixing before calling the fleet scenario production-ready are MinIO's abandoned-image risk and real video-concurrency numbers to size MediaMTX correctly — everything else is a normal vertical-scaling story.

05

Cloud: single VM vs. decomposed services

Option A — single VM, full Compose stack

  • Simplest to operate, cheapest at pilot scale — no code changes from what exists today.
  • At fleet scale, this VM becomes a single point of failure for the whole fleet, and MinIO's abandoned-image risk stays yours to carry regardless.

Option B — decompose onto managed services

  • Postgres → managed (RDS / Azure Database for PostgreSQL / Cloud SQL): removes backup/patching/HA burden, same wire protocol, no app changes.
  • MinIO → real object storage (S3/Blob/GCS): resolves the abandoned-image/unpatched-CVE risk directly (§1), not just a licensing preference; small backend change since it already speaks the S3 API.
  • Redis → managed (ElastiCache / Azure Cache, or managed Valkey): removes the SSPL question outright.
  • Mosquitto / MediaMTX → stay self-hosted on the VM — lightweight, no licensing pressure, and a managed swap is a bigger migration for limited benefit at this scale.
Recommendation: Option A for the pilot — decomposing now is overhead with no payoff at one-bot scale. For the fleet scenario, decompose Postgres and object storage specifically (a partial Option B) — those two swaps resolve the two real risks found in §4, while Mosquitto/MediaMTX/backend/frontend stay on a VM still under direct control. One exception that applies at either scale: swap the MinIO image itself (§1) as soon as practical — that's a dead-upstream/security-patching problem, not a scale or licensing-preference decision, so it shouldn't wait for the fleet migration.
06

Host OS: Linux vs. Windows + WSL2

Native Linux (Ubuntu 22.04/24.04 LTS or Debian 12) with Docker Engine — recommended.

  • Every image in the stack (node:22-alpine, postgres:16-alpine, etc.) is already a Linux container; WSL2 just inserts a second virtualization layer with no offsetting benefit.
  • Getting Docker running smoothly on Windows means Docker Desktop, which requires a paid subscription for larger companies (§2) and adds GUI/updater overhead a headless server doesn't need.
  • Native Linux + Docker Engine is the lighter, standard target for production Compose deployments.
  • The only reason to choose Windows + WSL2 is an explicit client IT/compliance mandate for Windows Server.
07

Final verdict

Pilot — one bot, one vehicle

2 vCPU · 4–8 GB · 60–100 GB · $25–50/mo

Small cloud VM, nearest region to the client site, Linux + Docker Engine, full stack as one Compose deployment (Option A). Use the office laptop only as a stated-temporary bridge if the VM budget isn't approved yet. Reasoning: every self-hosted component is well within its comfortable range at this scale, decomposing to managed services has no payoff yet, and a cloud VM removes the on-prem operational burden — hardware failure, patching, backup mechanics, no remote way to recover a frozen machine — without a meaningful latency cost once verified.

Fleet — 30 bots, multiple sessions/day each, on-demand video

8–16 vCPU · 24–32 GB · managed DB + storage

Cloud, with Postgres and object storage moved to managed services (RDS/Cloud SQL + S3/Blob) while Mosquitto, MediaMTX, backend, and frontend stay on a right-sized VM, plus budgeting the Tailscale Standard plan (or a Headscale decision) into the proposal now — not later. Reasoning: on-demand video still keeps the hardware bar well below a worst-case always-on estimate, but 30 confirmed bots each running several sessions a day raises sustained Postgres write volume and object-storage growth well past the earlier 15+ working estimate, which is why vCPU/RAM moved up from §3's original range. Postgres write throughput, disk growth rate, and MinIO's licensing trajectory are the three things actually worth resolving at this scale — a single self-hosted VM becomes a real single point of failure for a fleet this size, and managed DB/storage removes that along with the AGPL exposure.
