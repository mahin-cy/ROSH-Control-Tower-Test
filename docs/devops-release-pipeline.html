RoshAI Release Pipeline

How code moves from a feature branch to the dev VM and then to production. Every change is checked, built once, run on dev, and promoted to prod by a tagged, approved release. No one has to SSH into a server to deploy.

Strategy

Today the cloud prod VM is deployed by hand. Someone SSHes in, pulls the repo, edits docker/.env, builds images on the VM with docker compose up --build, and then builds a separate image just to run migrations. There's no CI, no image registry, no record of what is deployed, and no quick way back to the previous version.

What's changing. Dev is moving to an organization VM that may be in the cloud or on-prem behind a corporate firewall. The pipeline has to work the same on both. That rules out anything that needs inbound access to the server.

Principles behind the design

  • Build once, promote the same image. The frontend calls the API with relative paths and the backend reads all config from env vars, so one image works in both environments. Prod runs the exact bytes that were tested on dev.
  • VMs only pull and run. Builds run on GitHub's machines. The VMs never compile anything, so they stay small and predictable.
  • Untrusted code never reaches a server. Pull requests and CI run on GitHub-hosted runners. The self-hosted runners on our VMs pick up only deploy jobs, and only through a protected environment.
  • Every deploy can be undone. Each release is an immutable image tag, so rolling back means redeploying an earlier tag.
  • Nothing about Tailscale changes. The app stays reachable only over the tailnet. The runner talks to GitHub, not to the tailnet.

Why not the alternatives

OptionWhy we didn't pick it
GitHub runner joins the tailnet and SSHes inWorks, but it needs SSH open on every VM and a Tailscale OAuth key stored in GitHub, and it breaks if the org VM's network blocks it. The self-hosted runner needs neither.
Watchtower or another auto-pull agentIt can't run migrations, take a backup first or wait for approval, and it gives no visible pass/fail record.
Kubernetes with Argo CDFar more to operate than a single-VM Docker Compose stack needs. Revisit if the fleet outgrows one host.
Keep deploying by handNot repeatable, has no audit trail, and can't promote a tested build.

Compose change

Local dev still builds from source. On the VMs, compose pulls the tagged image instead.

docker/docker-compose.yml (excerpt)
backend:
  image: ghcr.io/rosh-ai-private-limited/roshai-control-tower-backend:${IMAGE_TAG:-local}
  build:
    context: ..
    dockerfile: docker/backend.Dockerfile
  restart: unless-stopped

frontend:
  image: ghcr.io/rosh-ai-private-limited/roshai-control-tower-frontend:${IMAGE_TAG:-local}
  build:
    context: ..
    dockerfile: docker/frontend.Dockerfile
  restart: unless-stopped

We also pin bluenviron/mediamtx:latest-ffmpeg, tecnativa/docker-socket-proxy:latest and tailscale/tailscale:stable to exact versions. Otherwise an upstream release could quietly change prod on the next deploy.

Dev deploy workflow

.github/workflows/deploy-dev.yml
name: deploy-dev
on:
  push:
    branches: [development]
  workflow_dispatch:
    inputs:
      image_tag: { description: "Existing tag to redeploy", required: true }

jobs:
  build:
    if: github.event_name == 'push'
    uses: ./.github/workflows/_build-images.yml
    permissions: { contents: read, packages: write }

  deploy:
    needs: build
    if: always() && (needs.build.result == 'success' || needs.build.result == 'skipped')
    uses: ./.github/workflows/_deploy.yml
    with:
      environment: dev
      image_tag: ${{ inputs.image_tag || format('sha-{0}', github.sha) }}

Release workflow (dev, then approval, then prod)

.github/workflows/release.yml (core)
name: release
on:
  push:
    tags: ["v*.*.*"]

jobs:
  guard:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - name: Tag must be on main
        run: git merge-base --is-ancestor "$GITHUB_SHA" origin/main

  build:
    needs: guard
    uses: ./.github/workflows/_build-images.yml
    permissions: { contents: read, packages: write }
    with: { version_tag: "${{ github.ref_name }}" }

  deploy-dev:
    needs: build
    uses: ./.github/workflows/_deploy.yml
    with: { environment: dev, image_tag: "${{ github.ref_name }}" }

  deploy-prod:
    needs: deploy-dev            # pauses here for prod reviewers
    uses: ./.github/workflows/_deploy.yml
    with: { environment: prod, image_tag: "${{ github.ref_name }}" }

Reusable deploy job

It runs on the VM's own runner and receives that environment's secrets only.

.github/workflows/_deploy.yml
on:
  workflow_call:
    inputs:
      environment: { type: string, required: true }
      image_tag:   { type: string, required: true }

jobs:
  deploy:
    runs-on: [self-hosted, linux, "roshai-${{ inputs.environment }}"]
    environment: ${{ inputs.environment }}
    concurrency: { group: "deploy-${{ inputs.environment }}", cancel-in-progress: false }
    permissions: { contents: read, packages: read }
    steps:
      - uses: actions/checkout@v4
      - name: Write .env
        env: { DOTENV: "${{ secrets.DOTENV }}" }
        run: |
          umask 077
          mkdir -p /opt/roshai-control-tower/docker
          printf '%s\n' "$DOTENV" > /opt/roshai-control-tower/docker/.env
      - name: Deploy
        env:
          GHCR_TOKEN: ${{ github.token }}
          DEPLOY_ENV: ${{ inputs.environment }}
        run: bash deploy/deploy.sh "${{ inputs.image_tag }}"

What a deploy does

deploy/deploy.sh runs on the VM. Each step has to pass before the next one starts. If any step fails, the job goes red and the earlier containers keep running.

  1. Copy the stack to a fixed folder. Sync docker/ into /opt/roshai-control-tower/docker/. The containers bind-mount the Mosquitto, Traefik and MediaMTX configs, and the runner wipes its own checkout on every job, so the stack must never run from there.

  2. Pull the images. Log in to GHCR with the job's short-lived token and pull backend and frontend at the requested tag.

  3. Back up prod. Start Postgres if it isn't running, then (prod only) pg_dump to /var/backups/roshai/, keeping the newest 14.

  4. Migrate. Run prisma migrate deploy from the new backend image. The runtime image already includes the Prisma CLI and migrations, so the separate migrate image from the runbook goes away.

  5. Start the stack. Run docker compose up -d --no-build --wait, which waits for every existing healthcheck to pass. If the Tailscale service definition changed, recreate tailscale, tailscale-cert-refresh, traefik and mediamtx together, because they share one network namespace.

  6. Smoke check. Hit the backend's /health from inside its container. A non-200 response fails the job.

  7. Record and clean up. Write the tag to /opt/roshai-control-tower/DEPLOYED and prune images older than 7 days.

deploy/deploy.sh (core)
#!/usr/bin/env bash
set -euo pipefail
TAG="$1"; ROOT=/opt/roshai-control-tower
rsync -a --delete --exclude .env docker/ "$ROOT/docker/"
cd "$ROOT"
export IMAGE_TAG="$TAG"
dc() { docker compose -f docker/docker-compose.yml "$@"; }

echo "$GHCR_TOKEN" | docker login ghcr.io -u "$GITHUB_ACTOR" --password-stdin
dc pull backend frontend
dc up -d --wait postgres

if [ "$DEPLOY_ENV" = prod ]; then
  mkdir -p /var/backups/roshai
  dc exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
    | gzip > "/var/backups/roshai/pre-$TAG-$(date +%Y%m%d%H%M).sql.gz"
  ls -1t /var/backups/roshai/*.sql.gz | tail -n +15 | xargs -r rm --
fi

dc run --rm --no-deps backend npx prisma migrate deploy --schema backend/prisma/schema.prisma
dc up -d --no-build --wait --wait-timeout 300
dc exec -T backend node -e "require('http').get('http://localhost:3000/health',r=>process.exit(r.statusCode===200?0:1)).on('error',()=>process.exit(1))"

echo "$TAG" > "$ROOT/DEPLOYED"
docker image prune -af --filter until=168h
Migrations only move forward. Rolling back an image does not undo a database migration. Write migrations so the previous release still works with the new schema (add columns before removing them). For prod, the pre-deploy pg_dump is the safety net.

Seeding is not part of the pipeline. prisma db seed runs once, when a new environment is first bootstrapped, and stays a manual runbook step.

One-time setup

In GitHub (repo admin)

  1. Confirm the repo is private. Never attach self-hosted runners to a public repo, because anyone could open a PR that runs code on our servers.

  2. Create the dev environment. Under Settings → Environments, limit deployments to the development branch and v* tags. Add a secret DOTENV containing the full dev .env, using docker/.env.example as the template.

  3. Create the prod environment. Limit deployments to v* tags only, add required reviewers (at least one person other than the release author, where possible), and add a secret DOTENV with the prod values.

  4. Protect the branches. On main and development, require the ci check to pass and block direct pushes to main.

  5. Check package visibility. After the first build, confirm both GHCR packages are private and linked to the repo, so the deploy job's token can pull them.

On each VM (dev and prod)

You need Ubuntu (or another Linux) with Docker Engine and the Compose plugin, plus outbound 443 to github.com, *.actions.githubusercontent.com, ghcr.io and pkg-containers.githubusercontent.com. No inbound ports are needed.

  1. Create a dedicated runner user and the deploy and backup folders.

    sudo useradd -m -s /bin/bash gh-runner
sudo usermod -aG docker gh-runner
sudo mkdir -p /opt/roshai-control-tower /var/backups/roshai
sudo chown gh-runner:gh-runner /opt/roshai-control-tower /var/backups/roshai

    Membership in the docker group is effectively root. That's acceptable because this user exists only to deploy this stack.

  2. Install the runner. In GitHub, go to Settings → Actions → Runners → New self-hosted runner (Linux x64) and run the download commands it shows as gh-runner. Then register it with the right label:

    ./config.sh --url https://github.com/Rosh-Ai-Private-Limited/roshai-autopdi-control-tower \
  --token <registration-token> \
  --name roshai-dev-vm --labels roshai-dev --unattended
# on the prod VM use: --name roshai-prod-vm --labels roshai-prod

  3. Run it as a service so it survives reboots.

    sudo ./svc.sh install gh-runner
sudo ./svc.sh start
sudo ./svc.sh status

  4. Check it's online. The runner should show as Idle under Settings → Actions → Runners.

Cutting over the existing prod VM

The compose project is fixed as name: roshai-control-tower. The pipeline's deploy therefore reuses the existing volumes (pgdata, miniodata, tailscale-state and the rest) from the new folder, and no data moves. Take a manual pg_dump first anyway. Once the first pipeline deploy is healthy, archive the old git-clone folder so nobody deploys from it by hand.

Day-to-day use

I want to…Do this
Ship a change to devMerge the feature PR into development. Dev updates in a few minutes.
Release to prodMerge development into main, then git tag v0.3.0 && git push origin v0.3.0. Check dev, then approve the waiting prod job in the Actions tab.
Roll back prodActions → release → Run workflow, enter the previous tag (for example v0.2.1), then approve.
Roll back devActions → deploy-dev → Run workflow with an earlier sha-… or v… tag.
Change a secret or env valueEdit DOTENV in that environment's settings, then re-run the latest deploy. Nothing is edited on the VM.
See what's runningCheck the environment's deployment history in GitHub, or cat /opt/roshai-control-tower/DEPLOYED on the VM.
Restore prod dataGunzip the matching file from /var/backups/roshai/ into psql inside the postgres container. Follow the runbook, and stop the backend first.
MQTT topic changes need coordination. Releases that change topics bots depend on (for example the multi-vehicle rename) still need a deploy time agreed with the bot team. The pipeline makes the deploy repeatable; it doesn't make a breaking contract change safe.

Rollout plan

Phase 1 · CI only

  • Add ci.yml and branch protection.
  • Nothing deploys yet. Every PR gets checked.

Phase 2 · Registry and dev deploy

  • Make the compose change and add the build workflow and deploy script.
  • Set up the org dev VM with a runner and the dev environment.
  • Merges to development now deploy automatically.

Phase 3 · Prod cut-over

  • Install a runner on the prod VM and create the prod environment with reviewers.
  • Take a manual backup, then cut v1.0.0, approve it, and confirm the volumes and data are intact.
  • Retire manual deploys.

Phase 4 · Hardening

  • Copy backups off the VM, for example a nightly sync to Blob or S3. Today they live on the same disk as the data.
  • Send failed-deploy notifications to the team channel.
  • Add image vulnerability scanning (for example Trivy) to CI.
  • Add a test stage once a test framework is chosen.

Verification

  • Run actionlint on .github/workflows/; it reports no errors.
  • A PR with a lint error fails ci and can't be merged. Fixing the error turns it green.
  • A merge to development pushes images to GHCR and deploys to dev. docker compose ps shows every service healthy.
  • The dev tailnet URL loads, password login works, and tools/bot-simulator.ts pointed at dev shows live telemetry.
  • A release candidate tag deploys to dev and then waits at the prod approval gate.
  • After approval, prod shows the new tag in DEPLOYED, and a new pg_dump file exists.
  • Rollback drill: redeploying the previous tag puts the old image digest back on prod (check with docker inspect).
  • Failure drill: a build with a broken /health turns the job red and doesn't touch the infra containers.

Open items

  • Container runtime on the org VM. The pipeline assumes Docker Engine on Linux. If the organization's IT only allows Docker Desktop with WSL2, or Podman, the runner still works, but deploy.sh has to be checked there first. This is the parked Docker runtime item in CLAUDE.md.
  • Secret manager. GitHub Environment secrets are masked and scoped, which is fine at this scale. Move to Azure Key Vault or similar if the client requires secrets to stay in their own tenant.
  • Plan quotas. Jobs on our own runners don't use GitHub Actions minutes, but builds on GitHub-hosted runners and private GHCR storage count against the org's plan. Check the plan's limits once the pipeline is running.
  • Tests. The framework is still undecided. The pipeline has a place ready for a test stage.
