MQTT Multi-Vehicle Topic Contract

Topic scheme update for fleet support — every robot/AUTO/… topic changes. This is a finalized contract, not a request for design input.

Scope Topic strings only — no payload/wire-format changes
Wire format Protocol Buffers (proto3), unchanged
Source of truth shared/src/mqtt/topics.ts
Target scale ~30 bots/vehicles within 6–12 months
On this page Context Topic table Firmware requirements Open questions Cutover coordination

01Context

We're extending the control tower to support a fleet of roughly 30 bots/vehicles over the next 6–12 months, up from today's single-vehicle pilot. Today's robot/AUTO/… convention (one fixed topic per message type, vehicle identity carried in the payload) doesn't scale to two things: commands meant for one specific vehicle need to reach only that vehicle, not every connected bot, and the topics that were never really vehicle-specific carried a name that implied otherwise.

This is a topic-string-only change. No payload or protobuf field changes anywhere, and no new identifiers are introduced — every topic still identifies a vehicle using the same vin_number you already send today.

02Topic table

Three topics become per-vehicle (backend→bot, targeted at one vehicle); five stay fixed and shared, just without the now-meaningless AUTO segment.

Message Direction Old topic New topic
Handshake request bot→backend robot/AUTO/handshake/request robot/handshake/request
Handshake response backend→bot robot/AUTO/handshake/response robot/{vin}/handshake/response
Heartbeat backend→all bots robot/AUTO/heartbeat robot/heartbeat
Telemetry bot→backend robot/AUTO/telemetry robot/telemetry
Command / e-stop backend→bot robot/AUTO/command robot/{vin}/command
Stop event bot→backend robot/AUTO/stop-event robot/stop-event
Video control backend→bot robot/AUTO/video/control robot/{vin}/video/control
Video status bot→backend robot/AUTO/video/status robot/video/status

{vin} is the same value you already send in your handshake/telemetry payloads — no new field, no new identifier.

Why the split: the three {vin}-templated topics are messages we send to one specific vehicle. Scoping them per-vehicle means the broker only ever delivers them to the bot that should receive them — most importantly, so an e-stop meant for one vehicle can never reach another once multiple bots are connected. The other five were always fleet-shared (many bots publishing/receiving on the same topic is fine), so they just lose the AUTO segment.

03Firmware requirements

  1. Subscribe/publish using the new strings above, substituting your own vin into the {vin} slot on the three templated topics.
  2. Ordering requirement on handshake/response specifically: subscribe to your own robot/{vin}/handshake/response before or at the same moment as publishing your handshake/request. MQTT does not redeliver a message to a client that subscribes after it was published — under the old shared-topic convention this didn't matter (every bot received every ack), but now your ack only ever goes to the one bot subscribed to that specific vin's topic.
  3. New convention — re-handshake after any reconnect, not only after power-on, including recovering from a transient network/SIM drop. Since telemetry carries no session identifier, this is how we distinguish "the same session resuming" from unrelated data arriving on our side.

04Open questions

  • MQTT retain flag usage

    Does any bot-published topic (telemetry, stop-event, video-status, handshake-request) use retain=true today? We're assuming not — if any do, a shared topic would retain only the most recent publisher's message, which we'd need to handle differently.

  • Was AUTO a template or a literal?

    Was AUTO always meant as a firmware template placeholder, or is it a hardcoded literal in your current build? Informational only — helps us gauge the actual firmware effort, doesn't change what we're asking for.

05Cutover coordination

No backwards-compatible bridge: once our backend switches over, the current pilot vehicle (TEST-VIN-001) will stop sending/receiving on every one of these channels until its firmware adopts the new strings.

We'd like to propose a coordinated cutover date/version and get your firmware deployment scheduled to land at or before it, rather than a silent release on our end. Please confirm a target date, and whether this is a config-only change or requires a new firmware build.
