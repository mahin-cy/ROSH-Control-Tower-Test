Session Audio Contract

At the end of each test run the bot uploads its report, then asks the control tower whether the audio is wanted. It uploads the audio only on a yes, and sends session-end last, as it does today.

01Overview

The bot records audio during each test run, roughly 50–500 MB per session as WAV. Nothing is uploaded while driving, so live video and telemetry keep the SIM uplink to themselves.

When the physical run ends, the bot uploads the PDF report as it does today, then tells the control tower the audio is ready and waits. The control tower asks its admins and operators whether they want it:

  • Yes: the bot uploads the audio, then sends session-end.
  • No: the bot sends session-end straight away.
  • Cancel during the upload: the bot stops and sends session-end.
  • No answer in time: the bot sends session-end.
session-end stays the bot's last message, exactly as today. The whole audio phase happens inside the session, so the bot never needs to remember anything for later and never changes vehicle mid-way. Keeping or deleting audio on the bot afterwards, and any “uploading” indicator on the hardware, are the bot team's decision.

02End-of-run sequence

  1. Physical run ends
    The vehicle stops. The session stays open. Keep sending telemetry (see section 03).
  2. Upload the PDF report
    Exactly as today, POST /api/v1/vehicles/{vin}/reports.
  3. Announce the audio
    Close the audio file (including its final header), compute its SHA-256, and publish AudioReady. If the run has no audio, skip to step 5.
  4. Wait for the decision
    Wait up to decision_window_s for a command on robot/{vin}/audio/control:
    • FETCH: upload the file (section 08). On success, send COMPLETED.
    • CANCEL, while waiting or while uploading: stop, send CANCELLED.
    • Nothing within the window: send EXPIRED.
  5. Send session-end, then disconnect
    As today. Nothing is sent after this.

Meanwhile the web app shows every online user “Download audio for this run? (320 MB)” with a countdown based on decision_window_s. The first answer wins. While the audio phase runs, the vehicle is shown as “Run finished · uploading audio”, not as driving.

03Keeping the session alive

Today the control tower uses telemetry to tell whether a bot is still there. An active session with no telemetry for 30 seconds is marked lost contact. The audio phase can last many minutes, so something has to keep the session alive during it.

Preferred: keep telemetry running until session-end

  • Keep publishing telemetry at 1 Hz through the report, the wait and the upload, and stop only when you send session-end.
  • It's a few hundred bytes per second, negligible next to the upload, and while parked it's real data (speed 0).
  • Nothing changes on the server: a crash or power cut is still detected within 30 seconds.

Fallback, if telemetry can't continue after the run

If your telemetry comes from parts of the driving stack that shut down when the run ends, tell us (Q2). The control tower will then keep the session alive itself, using these timeouts instead:

PhaseWhat the server watchesMarked lost contact after
Report upload (before AudioReady)Nothing new yetThe normal 30 s after the last telemetry
Waiting for a decisionNothing (the bot is silent)decision_window_s + 60 s with no status or session-end
UploadingUpload chunks arriving2 minutes with no new data

Under the fallback, publish AudioReady within 30 seconds of the last telemetry message. Do the report first only if it reliably takes less than that. Crashes are then detected in minutes rather than seconds, which is acceptable for a parked vehicle.

04File naming

One run is identified by (vin, mac_id, session_id), the same identity already used for sessions and PDF reports.

formatone file per session
{vin}_{macId}_{sessionId}.{ext}        // ext = wav | flac | opus

Before joining the parts, replace every character outside [A-Za-z0-9_-] in each part with _. This is the same rule the control tower uses for report file names. For example, the MAC 00:1A:2B:3C:4D:5E becomes 00_1A_2B_3C_4D_5E:

TEST-VIN-001_00_1A_2B_3C_4D_5E_1760000000.wav
VINMAC IDSession ID

05Topics and messages

Audio gets its own channel, the same way video already has video/control and video/status. The e-stop message (command.proto) and the handshake (session.proto) are not changed. Everything new is in one file, audio.proto.

TopicDirectionQoSMessage
robot/audio/ready bot → backend 1 AudioReady
robot/{vin}/audio/control backend → bot 1 AudioControlCommand
robot/audio/status bot → backend 1 AudioStatus
Subscribe to robot/{vin}/audio/control at QoS 1, together with the existing handshake-response and command topics, before publishing the handshake. MQTT delivers at the lower of the publish and subscribe QoS, so a QoS 0 subscription would silently downgrade our commands. As with the command topic, only the backend can publish on audio/control.
audio.proto — new fileproto3
syntax = "proto3";
package roshai.mqtt.v1;

// robot/audio/ready — bot → backend, once per run, after the report
message AudioReady {
  string vin_number        = 1;
  string mac_id            = 2;
  string session_id        = 3;
  string file_name         = 4;  // exactly as in section 04
  uint64 size_bytes        = 5;
  string sha256            = 6;  // lowercase hex, of the finished file
  string format            = 7;  // "wav" | "flac" | "opus"
  string recorded_at       = 8;  // ISO-8601 UTC, session start time
  uint32 decision_window_s = 9;  // how long the bot will wait for FETCH
}

enum AudioControlAction {
  AUDIO_CONTROL_ACTION_UNSPECIFIED = 0;
  AUDIO_CONTROL_ACTION_FETCH       = 1;  // user wants the audio: upload it
  AUDIO_CONTROL_ACTION_CANCEL      = 2;  // user said no, or stopped the upload
}

// robot/{vin}/audio/control — backend → bot
message AudioControlCommand {
  string vin_number = 1;  // same as the topic, cross-check
  AudioControlAction action = 2;
  string session_id = 3;
  string file_name  = 4;
  string upload_url = 5;  // FETCH only, e.g. https://<host>/api/v1/audio/uploads
  string command_id = 6;  // echo back in AudioStatus
  string issued_at  = 7;  // ISO-8601 UTC
}

enum AudioTransferState {
  AUDIO_TRANSFER_STATE_UNSPECIFIED = 0;
  AUDIO_TRANSFER_STATE_UPLOADING   = 1;
  AUDIO_TRANSFER_STATE_COMPLETED   = 2;
  AUDIO_TRANSFER_STATE_CANCELLED   = 3;
  AUDIO_TRANSFER_STATE_EXPIRED     = 4;  // no FETCH within the decision window
  AUDIO_TRANSFER_STATE_NOT_FOUND   = 5;
  AUDIO_TRANSFER_STATE_ERROR       = 6;
}

// robot/audio/status — bot → backend
message AudioStatus {
  string vin_number    = 1;
  string mac_id        = 2;
  string session_id    = 3;
  string file_name     = 4;
  AudioTransferState state  = 5;
  uint64 bytes_sent    = 6;
  string error_message = 7;  // set for ERROR
  string command_id    = 8;  // from the command that triggered this, if any
}

06Handling commands

ActionWhat the bot doesReplies, then
FETCH
  1. Check that session_id and file_name match the file you announced. Reject anything containing a path separator.
  2. If the file is missing, reply NOT_FOUND.
  3. Stop the decision timer and upload as in section 08.
  4. If the upload is already running, ignore the duplicate.
 UPLOADING → COMPLETED, then session-end
CANCEL Stop waiting, or stop sending upload data (check between chunks). There's no need to clean up on the server; the control tower removes the partial upload itself. CANCELLED, then session-end
QoS 1 can deliver a command twice. Both actions are safe to repeat: a duplicate FETCH is ignored, and a CANCEL that arrives after you've finished can be ignored.

07Reporting status

Publish AudioStatus on robot/audio/status only when the state changes. The control tower tracks upload progress itself, so per-chunk messages aren't needed. Every state except UPLOADING is final: send session-end next.

COMPLETEDThe final PATCH returned 204 (the server verified the file)session-end

08Upload with tus 1.0.0

The upload goes to the upload_url from the FETCH command, over the same tailnet hostname and port 443 as the PDF report upload. There is no authentication, the same as today. tus is a small open HTTP protocol for resumable uploads (tus.io). Here it lets an upload survive SIM drop-outs within the session. It takes three request types, all of which libcurl handles.

1. Create the upload

request → responseHTTP
POST {upload_url}
Tus-Resumable: 1.0.0
Upload-Length: <size_bytes>
Upload-Metadata: vin <b64>,macId <b64>,sessionId <b64>,fileName <b64>,sha256 <b64>

→ 201 Created
Location: <upload URL>        // keep this for the rest of the upload

Metadata values are base64-encoded.

2. Send the data in 5–8 MB chunks

request → responseHTTP
PATCH <upload URL>
Tus-Resumable: 1.0.0
Content-Type: application/offset+octet-stream
Upload-Offset: <current offset>

<chunk bytes>

→ 204 No Content
Upload-Offset: <new offset>

3. Resume after a dropped connection

request → responseHTTP
HEAD <upload URL>
Tus-Resumable: 1.0.0

→ 200 OK
Upload-Offset: <n>            // continue PATCHing from here

Responses and what to do

ResponseMeaningBot action
204 on the final PATCHFile received and SHA-256 verifiedSend COMPLETED
460Checksum mismatchStart again from step 1, once. If it fails again, send ERROR.
409Offset mismatchRun HEAD to get the correct offset, then continue
404 / 410The upload was cancelled or expired on the serverStop. A CANCEL is normally on its way.
403The server didn't request this fileStop and send ERROR
5xx / network errorTemporary failureRetry with backoff, then resume with HEAD

libcurl notes

  • For PATCH, use CURLOPT_CUSTOMREQUEST "PATCH" with CURLOPT_UPLOAD and CURLOPT_READFUNCTION, reading from the file at the current offset.
  • Detect stalled links with CURLOPT_LOW_SPEED_LIMIT and CURLOPT_LOW_SPEED_TIME, for example under 1 KB/s for 30 s.
  • Retry with backoff from 1 s up to 60 s. Give up and send ERROR after a limit you choose (we suggest 15 minutes without progress).
  • Check for a CANCEL between chunks, so a cancel takes effect within one chunk.

09Behaviour rules

  1. session-end is always last. Don't send it until the audio phase has reached a final state (section 07). If the run has no audio, send it straight after the report, as today.
  2. Allow enough time to shut down. If the end of a test is triggered by an OS shutdown, the service manager (systemd) usually force-kills the process about 90 seconds after the stop signal. The audio phase needs longer, so raise that limit or run the end-of-run sequence before stopping the service (Q1).
  3. Keep the session alive as described in section 03.
  4. One audio file per run, uploaded at most once.
  5. Network drops are resumed within the session (section 08). A power cut or crash ends the session; the audio stays on the bot, and what happens to it is your decision. There's no automatic resume in this version.
  6. Local files and any hardware indicator are yours to decide. This contract never asks the bot to delete anything.

10Acceptance tests

Run these against the dev control tower (control-tower-dev) before the field test.

  • Order

    At run end: report, then AudioReady, then the audio phase, then session-end as the very last message.

  • Yes

    FETCH leads to UPLOADING, COMPLETED, then session-end. The web app shows the file as verified.

  • No

    CANCEL while waiting leads to CANCELLED and session-end within a few seconds.

  • Cancel mid-upload

    CANCEL during an upload stops it within one chunk, then CANCELLED and session-end.

  • Nobody answers

    With no command, the bot sends EXPIRED when the window ends, then session-end.

  • Session stays alive

    During a long upload the session never shows as lost contact (telemetry continues, or the fallback applies).

  • Network drop

    Pull the network mid-upload and restore it. The upload continues from the last offset, not from zero.

  • Long shutdown

    Ending a test through the normal shutdown path with a 300 MB upload completes without the process being killed.

  • Repeated commands

    A duplicate FETCH doesn't start a second upload, and a late CANCEL after COMPLETED is ignored.
