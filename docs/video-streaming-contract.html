01Overview

Two new MQTT topics let the control tower start and stop the bot's camera stream and adjust its quality. The video itself never touches MQTT — it travels over RTSP directly from the bot to our media server, MediaMTX (browser playback on our side is WebRTC, but that's downstream of MediaMTX and none of your concern). MQTT carries only the small control signal: when to stream, at what quality, and where to push it.

Updated Sep 2026: ingest is RTSP, not WHIP as originally proposed — your Jetson's Ubuntu/GStreamer version predates WHIP's GStreamer ≥1.22 requirement, so WHIP wasn't actually usable on your hardware. RTSP push (rtspclientsink) has no such version requirement, so it's the direct substitute — see GStreamer pipeline.

This follows the same convention as your other topics: fixed robot/AUTO/… paths, per-vehicle identity carried in the payload rather than the topic, Protobuf on the wire. Build against it, but treat it as a proposal — the same way heartbeat, telemetry, and command started as our guesses and got corrected once tested against real hardware.

02Topics

Both topics are QoS 1, not QoS 0 like heartbeat/telemetry — a dropped start/stop is a real failure (the stream never starts, or never stops), not a tolerable missed reading.

TopicDirectionQoSPayload message
robot/AUTO/video/control backend → bot 1 VideoControlCommand
robot/AUTO/video/status bot → backend 1 VideoStatus
You subscribe to video/control and publish to video/status — mirror image of how you already handle command vs. stop-event.

03Protobuf schema

Authoritative definition, copied verbatim from shared/proto/video.proto. Field numbers are what matter for wire compatibility — names are cosmetic.

video.protoproto3
syntax = "proto3";
package roshai.mqtt.v1;

enum VideoAction {
  VIDEO_ACTION_UNSPECIFIED = 0;
  VIDEO_ACTION_START = 1;
  VIDEO_ACTION_STOP = 2;
  VIDEO_ACTION_SET_BITRATE = 3;
}

message VideoControlCommand {
  string vin_number = 1;
  string session_id = 2;
  string command_id = 3;          // echo this in your VideoStatus reply
  VideoAction action = 4;
  uint32 target_bitrate_kbps = 5; // set only on START / SET_BITRATE
  uint32 target_width = 6;        // set only on START / SET_BITRATE
  uint32 target_height = 7;       // set only on START / SET_BITRATE
  uint32 target_fps = 8;          // set only on START / SET_BITRATE
  string ingest_url = 9;          // RTSP push target, START / SET_BITRATE only
  int64  issued_at_ms = 10;        // epoch ms
}

enum VideoState {
  VIDEO_STATE_UNSPECIFIED = 0;
  VIDEO_STATE_STARTING = 1;
  VIDEO_STATE_STREAMING = 2;
  VIDEO_STATE_STOPPED = 3;
  VIDEO_STATE_ERROR = 4;
}

message VideoStatus {
  string vin_number = 1;
  string session_id = 2;
  string command_id = 3;          // the command_id you're responding to
  VideoState state = 4;
  uint32 current_bitrate_kbps = 5;
  uint32 current_width = 6;
  uint32 current_height = 7;
  string error_message = 8;       // only when state == VIDEO_STATE_ERROR
  int64  reported_at_ms = 9;
}

Field reference — what to do with each one

Same fields as above, framed as "what do I actually do with this" rather than just the type.

VideoControlCommand — arrives on robot/AUTO/video/control

FieldPurposeWhat the bot does with it
vin_number Which vehicle this command is for Read-only — confirms it's addressed to you (today there's only one bot, so always matches)
session_id Ties this command to the active test session Read-only — copy unchanged into your VideoStatus reply
command_id Unique ID for this specific command Must copy exactly into the command_id of the VideoStatus you send back — this is how we match your reply to the command that triggered it
action What to actually do START → begin the pipeline. STOP → tear it down. SET_BITRATE → adjust the running pipeline, or restart it with new values if live reconfig isn't supported
target_bitrate_kbps Desired bitrate, in kbps Set as the encoder's target bitrate (×1000 for GStreamer's bitrate property, which wants bits/sec). Only present on START/SET_BITRATE
target_width, target_height Desired resolution, in pixels Configure the camera/encoder output to this size. Only present on START/SET_BITRATE
target_fps Desired frame rate Configure the pipeline's capture/encode rate. Only present on START/SET_BITRATE
ingest_url Exact URL to push the RTSP stream to Plug directly into rtspclientsink's location — don't hardcode your own URL, always use whatever arrives in this field. Only present on START/SET_BITRATE
issued_at_ms When this command was sent (epoch ms) Optional, defensive use only: if a command's timestamp is older than one you've already acted on, it's safe to ignore — it arrived late after a network hiccup

VideoStatus — you publish this on robot/AUTO/video/status

FieldPurposeWhat value to send
vin_number Identifies your vehicle Same VIN you already use in handshake/telemetry
session_id Ties this report to the session Echo back the current session's ID
command_id Which command this is a reply to Must exactly match the command_id from the triggering VideoControlCommand
state What your pipeline is actually doing right now STARTING immediately after START, while spinning up → STREAMING once the RTSP push is actually connected and frames are flowing → STOPPED after tearing down → ERROR if anything failed
current_bitrate_kbps, current_width, current_height What's actually being streamed The pipeline's real live values — mainly relevant when state: STREAMING; may differ slightly from the requested targets if the encoder rounds to a supported value
error_message Why it failed Only fill in when state: ERROR — a short, specific reason: "camera not found", "pipeline failed to start", "RTSP push rejected". Leave empty otherwise
reported_at_ms When this report was generated Current time (epoch ms) at the moment you publish
The one rule that matters most: every VideoStatus you send should carry the command_id of whatever command it's responding to — that's the thread that lets our UI show “starting…” → “live” instead of a black box.

04Message flow

What a typical session looks like, start to finish. Video is not continuous — it runs only while at least one operator has the vehicle's live page open, so expect repeated start/stop cycles within one test run, not a single stream for the whole session.

  1. Operator opens the vehicle's live page
    Control tower backend receives its first viewer for this vehicle.
  2. Backend publishes VIDEO_ACTION_START
    On robot/AUTO/video/control, with target bitrate/resolution/fps and an ingest_url to push to.
  3. Bot replies STARTING
    On robot/AUTO/video/status, echoing the command's command_id, while the pipeline spins up.
  4. Bot pushes H.264 via RTSP
    To the ingest_url from step 2 — see Video transport below.
  5. Bot replies STREAMING
    Once the RTSP push is actually connected — include current_bitrate_kbps/current_width/current_height.
  6. Last operator closes the page
    Backend publishes VIDEO_ACTION_STOP; bot tears the pipeline down and may reply STOPPED.

If anything fails at any point — camera not found, encoder error, RTSP push rejected — reply ERROR with a short error_message instead of going silent. That's what lets the operator UI show something more useful than an indefinite spinner.

05Video transport

Separate from MQTT entirely. On START:

  • Read the depth camera's RGB colour output only — not the depth/distance data, which stays on your side for perception.
  • Encode to H.264 using the Jetson's hardware encoder (nvv4l2h264enc).
  • Push via RTSP (the ANNOUNCE/RECORD publish flow) to the ingest_url supplied in the command.

On SET_BITRATE, reconfigure the running encoder live if your pipeline supports it, or restart with the new targets if not. On STOP, tear the pipeline down.

06GStreamer pipeline

rtspclientsink (the RTSP ANNOUNCE/RECORD publish flow) has shipped in gst-plugins-good for a long time — this is what replaces the WHIP approach originally proposed here, since your Jetson's Ubuntu/GStreamer version predates WHIP's GStreamer ≥1.22 requirement (whipclientsink). No version gate to check this time. If you hit a "no such element" error, confirm the plugin is present:

sanity checkbash
gst-inspect-1.0 rtspclientsink

Pipeline

pipelinebash
gst-launch-1.0 \
  <your-camera-RGB-source> ! \
  nvv4l2h264enc bitrate=4000000 ! \
  h264parse ! \
  rtspclientsink location="rtsp://roshai-control-tower.<tailnet-domain>:8554/AUTO" protocols=tcp

bitrate is bits/second, so target_bitrate_kbps × 1000. location should always be whatever arrives in that command's ingest_url — the value shown here is just today's default, don't hardcode it.

Important — use protocols=tcp. rtspclientsink defaults to negotiating UDP for the actual media (RTP), separate from the TCP control connection. We found this drops the session after ~10s over the tailnet in our own testing — forcing TCP-interleaved transport (media riding inside the same TCP connection as the RTSP control channel) fixed it immediately and reliably in a sustained test. It's also simpler for you: with protocols=tcp, only port 8554 matters for ingest — no separate UDP ports to worry about at all.
Update, Sep 2026 — root cause found and fixed server-side. The ~10s UDP drop above and a separate WebRTC playback failure (browser-side viewing never showed video despite signaling succeeding) turned out to share one cause: our Tailscale container was running without real kernel network access, so it silently fell back to a mode that can't properly carry UDP media. We've since granted it proper network access on our end, which should make raw UDP more reliable over the tailnet going forward. No action needed on your side — protocols=tcp remains the right, simplest choice for RTSP ingest regardless (fewer ports, no change requested), this is just context in case you were independently chasing the same class of symptom.
